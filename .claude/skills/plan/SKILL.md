# plan — Full Plan 계획 쓰기

요청: $ARGUMENTS

## 절차
1. `CLAUDE.md`(특히 §2 실행 방식 · §5 아키텍처 · §6 WebGL), 관련 `GDD.md` 절, `TDD.md` 해당 절, 관련 코드 · 테스트를 읽는다. 에디터 상태가 계획에 영향을 주면 MCP로 확인만 한다.
2. 요청을 요구사항 항목으로 나눈다. 사용자의 원래 요청 문장은 그대로 옮겨 적는다.
3. 실행 방식을 다시 판정한다. Full Plan이 아니면 이유를 말하고 멈춘다.
4. 계획을 `Docs/plans/YYYY-MM-DD-<영문-이름>.md`에 저장한다.

## 하지 말 것
- 코드 · 씬 · 에셋 · 설정 수정, 테스트 · 빌드 실행.
- 정해지지 않은 수치 · 기획을 임의로 확정하기 — "사용자에게 물을 것"에 적는다.
- 후보 기획(GDD §7)을 위한 인터페이스 · 설정 · 빈 클래스.

## 결과 형식 (계획 파일)
- 원래 요청(그대로) · 목표
- 요구사항(번호 목록)
- 수정 대상 — 기존 파일 / 새 파일 구분, 다시 돌릴 빌더(씬 · 폰트 · 그림 · 목록)
- 구현 단계 — 결과를 하나씩 확인할 수 있는 크기로. 단계마다 `목표 · 수정 대상 · 선행 단계 · 완료 기준 · 검증 방법`(EditMode 테스트 / 에디터 플레이 / WebGL 빌드 / 사용자 실기). 단계 수는 고정하지 않는다.
- 위험 — 회귀(포도 · 프로토타입 · 콘텐츠 회귀 테스트) · 저장 데이터 호환(머리줄 · 진행 기록 키) · 빌드 용량 · WebGL 제약
- 후보 기획(GDD §7)을 불가능하게 만드는지
- 사용자에게 물을 것

채팅에는 계획 파일 경로 · 요약 5줄 이내 · 물을 것만 쓴다. 검증은 셋으로 나눈다: 코드 · 테스트로 확인 / 화면으로 확인 / 확인 못 함.
