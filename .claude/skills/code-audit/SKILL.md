# code-audit — 전체 코드 점검 (읽기 전용, 새 세션)

인자: $ARGUMENTS

## 0. 인자
- 범위(필수):

| 인자 | 경로 | 함께 읽을 규칙 |
|---|---|---|
| `core` | `Assets/Scripts/Core` | CLAUDE.md §5 |
| `game` | `Assets/Scripts/Game` | CLAUDE.md §5 · §6, `.claude/rules/game-code.md` |
| `editor` | `Assets/Scripts/LevelEditor` | `.claude/rules/game-code.md` |
| `tests` | `Assets/Tests/EditMode` | CLAUDE.md §7 |
| `agent` | `AgentScripts` | `AgentScripts/README.md` |
| `all` | `core` → `game` → `editor` → `tests` 차례로(`agent`는 빠진다) | 위 각각 |

- 강도(선택): `low` · `medium` · `high` · `max`. 없으면 `medium`. `max`는 사용자가 이번 호출에 적었을 때만 쓴다. `ultra`는 받지 않는다(클라우드 · 사용자가 직접 실행).
- 범위가 없거나 표에 없으면 표를 보여 주고 멈춘다.

## 1. 준비
- 범위의 규칙 문서와 `Docs/TDD.md`의 해당 절을 읽는다. 범위의 `.cs` 파일 목록과 줄 수를 센다(보고에 쓴다).

## 2. 버그 리뷰 — 기본 `/code-review`
- `Skill`(skill=`code-review`, args=`<강도> <경로>`)로 부른다. `all`이면 영역마다 한 번씩. `--fix` · `--comment`는 붙이지 않는다.
- 결과가 변경분(diff)만 본 것으로 보이면(예: "변경 없음", 범위 파일 일부만 언급) 이 단계를 "확인 못 함 — 경로 대상이 파일 전체를 보지 않음"으로 적고 사용자에게 알린다. 이 스킬을 독립 방식(3단계만)으로 바꿀지 사용자가 정한다.

## 3. 프로젝트 관점 점검 — 직접 읽고 판단
범위의 파일을 직접 읽고 아래를 닫힌 질문으로 확인한다. 범위에 해당하지 않는 항목은 건너뛴다.
1. **규칙 복제**: 표현 계층 · 레벨 에디터가 붓질 · 색 혼합 · 막힘(`(cell & ~target) != 0`) · 성공 판정을 직접 계산하나? 붓질 계산이 `Board.Sweep` 한 곳뿐인가?
2. **런타임 탐색 상한**: 런타임에서 솔버 · 힌트 · 생성기를 부를 때 상태 수 상한이 있나? 한 프레임에 오래 도는 반복이 있나(여러 프레임에 나누는가)?
3. **저장 형식**: 머리줄 버전(`progress 1` · `stats 2` · `endless 1`)을 쓰고 확인하나? 깨진 입력 · 옛 형식을 처리하나? 그 처리를 테스트가 보나? 저장이 `IKeyValueStore` 뒤에 있나?
4. **진행 기록 키**: 스테이지 파일 이름에 기대는 코드에서 이름이 바뀌거나 겹치면 기록이 끊기거나 섞이나?
5. **하드코딩 색**: 표현 계층이 `Color` 리터럴 · 16진 색을 코드에 넣었나(팔레트 · `UiTheme`에서 읽어야 한다)? 디버그 · 에디터 전용 표시는 구분해 적는다.
6. **게임 코드 규칙**(`game` · `editor`): 매 프레임 할당(`new` · LINQ · 문자열 조합) · 이벤트 구독 해제 누락 · 플레이 재시작 때 남는 static 상태 · `Awake`/`Start` 밖 `GetComponent`/`Find` · Obsolete API.
7. **Core 순수성**(`core`): 로그 대신 반환값 · 예외로 알리나? 실패를 기본값으로 덮어 성공처럼 보이게 하나?
8. **테스트 공백**: 영향이 큰 동작(붓질 · 판정 · 솔버 · 저장 · 진행)인데 테스트가 없는 곳.
9. **데드코드 · 과한 구조**: 안 쓰는 코드, 후보 기획(GDD §7)을 위한 미리 만든 추상화 · 설정 옵션. 알리기만 한다.
- `SourceRuleTests`가 이미 잡는 금지 패턴(스레드 · `System.IO` · `PlayerPrefs` 직접 호출 · `LoadScene`)은 다시 찾지 않는다.
- 지적마다 파일 · 줄을 직접 열어 확인한다. 확인 못 한 것은 추정으로 표시한다.

## 4. 보고
1. 머리: 범위 · 강도 · 파일 수 · 줄 수 · 2단계가 파일 전체를 봤는지.
2. 지적 표: 심각도(**높음** = 버그 · 데이터 손실 · 규칙 위반 / **중간** = 위험 · 공백 / **개선** = 정리 · 단순화) · `파일:줄` · 내용 · 근거 · 제안 · 출처(`code-review` / 프로젝트 점검). 높음이 없으면 "높음 없음". 두 단계가 같은 것을 짚으면 하나로 합친다.
3. 확인한 사실과 추정을 나눈다.
4. 조치할 항목을 `Docs/Task.md`로 옮길지, 하지 않기로 한 것을 `Docs/DECISIONS.md`에 남길지 묻는다(CLAUDE.md §0).

## 하지 말 것
- 코드 · 문서 수정(사용자가 지적을 고르기 전), 테스트 · 빌드 실행, 커밋.
- 지적 개수 채우기, 근거 없는 지적, 취향 · 스타일을 동작 오류처럼 쓰기.
- 이 스킬을 구현한 세션 · 리뷰 대상을 고친 세션에서 돌리기(새 세션에서 — CLAUDE.md §8).
