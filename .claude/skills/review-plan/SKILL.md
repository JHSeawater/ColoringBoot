# review-plan — 계획 검수 (읽기 전용, 새 세션)

대상: $ARGUMENTS

## 절차
1. 계획 파일, 그 안의 원래 요청, 관련 코드 · 테스트, `CLAUDE.md`, 관련 `Docs/GDD.md` 절만 읽는다. 계획을 쓴 쪽의 결론을 정답으로 두지 않는다.
2. 원래 요청을 요구사항 항목으로 나눠 계획에서 반영된 위치와 대조한다.
3. 닫힌 질문으로 확인한다:
   - 빠진 요구사항이 있나?
   - 버그 · 데이터 손실 위험(저장 형식 · 진행 기록 키 = 스테이지 파일 이름)이 있나?
   - 검증 방법이 없는 단계가 있나?
   - `CLAUDE.md` 규칙(Core 순수 로직 · 씬은 빌더가 정본 · WebGL 단일 스레드 · 붓질 규칙)과 충돌하나?
   - 확정 기획(GDD)과 충돌하나? 후보 기획(GDD §7)을 불가능하게 만드나?
   - 요청 밖 기능 · 추상화가 있나?
4. 지적마다 근거(파일 · 줄)를 직접 열어 확인한다.

## 하지 말 것
- 코드 · 계획서 수정.
- 지적 개수 채우기, 근거 없는 지적, 취향 · 스타일을 동작 오류처럼 쓰기.
- 기획 판단, 요청하지 않은 기능을 필수 요구사항으로 만들기.

## 결과 형식
- 요구사항 대조표: 요구사항 · 반영 위치 · 상태(반영 / 부분 반영 / 누락 / 판단 불가) — 구현 누락과 검증 공백을 구분한다.
- 지적: 중요도(높음 · 보통 · 낮음) · 근거(파일:줄) · 제안. '높음'이 없으면 "높음 없음"이라고 쓴다.
- 확인한 사실과 추정을 나눈다.
- 사용자에게 물을 것
