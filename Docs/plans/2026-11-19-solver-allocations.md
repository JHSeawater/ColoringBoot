## 요구사항

1. 색이 안 바뀌는 획에 배열을 새로 만들지 않는다. 받아들인 후보(다음 층에 들어가는 상태)만 새 배열이 된다.
2. 같은 키를 `_seen`과 `_previous`에 이중으로 두지 않는다 — 방문 여부는 `_previous` 하나로 본다(시작 상태도 그 안에).
3. 막힌 후보 기억은 3단계에서 재 보고, 호박 막다른 길 힌트 시간(에디터)이 2단계보다 10% 이상 줄 때만 남긴다(사용자 답 1). 남기더라도 `Explored` · 경로 · 상한 시점은 지금과 같아야 한다(막힌 상태는 지금도 세지 않고 펼치지 않는다).
4. 탐색 결과가 바뀌지 않는다: 모든 게임(무한 모드 묶음 900판 포함) · 프로토타입 판의 시작 상태와 플레이 중간 상태에서 경로의 모든 획 · `Explored` · `Limited` · `DeadAtStart`가 옛 코드와 같다. 기존 EditMode 테스트 전부 통과.
5. 효과를 숫자로 남긴다: 호박 막다른 길 힌트 · 71판 시작 상태 풀이의 할당 바이트와 시간(에디터), 그리고 WebGL 빌드 · 배포 뒤 PC Chrome 힌트 시간(사용자 답 3).
6. 공개 API(`SolverSearch` 생성자 · `Step` · `Result`, `Solver.Solve`, `SolveResult`)와 "start 배열은 바꾸지 않는다" 약속은 그대로다. 이 약속은 테스트로 계속 지킨다(0단계에서 `SolverTests`에 더함).

### 1단계 — 버려지는 복사 없애기

- 목표: 요구사항 1.
- 수정 대상: `SolverSearch.Expand`.
- 선행: 0단계.
- 방법: 펼칠 상태를 작업 배열 하나(`_scratch`, 칸 수 크기)에 한 번 복사하고 획마다 그 위에 칠한다.
  - `Brush`가 false → 배열이 그대로라 다음 획에 그대로 쓴다(복사 없음).
  - 바뀌었지만 이미 본 상태 · 막힌 상태 → `Array.Copy(state, _scratch, n)`로 되돌린다.
  - 받아들임 → `_scratch`를 다음 층에 넣고, 새 작업 배열을 만들어 `state`를 복사한다(받아들인 상태 수만큼만 할당).

- 완료 기준: EditMode 전체 통과(start 불변 확인 포함) · 0단계 정답 파일(무한 모드 900판 포함)과 대조해 차이 0줄.
- 검증: EditMode(`SolverTests` · `GrapeRegressionTests` · `PrototypeStageRegressionTests` · `ContentRegressionTests` · `HintTests` · `EndlessTests` 먼저, 이어서 전체) + 정답 대조 스크립트.

## 위험

- **start 배열에 칠하는 실수**: 작업 배열 대신 `state`(첫 층에서는 세션의 화면 배열)에 칠하면 힌트를 누를 때 보드가 바뀐다. 정답 대조는 상태마다 새 배열을 쓰면 이를 못 잡는다 → `SolverTests`의 start 불변 확인(0단계).
- **결과가 바뀌는 회귀(가장 큼)**: 작업 배열을 되돌리지 않고 다음 획에 쓰면 엉뚱한 상태를 탐색한다. 탐색 순서가 바뀌면 같은 최소 수라도 다른 경로를 찾아 힌트의 첫 수가 달라지고, 프로토타입 `Explored`가 어긋난다. → 0단계 정답 파일(중간 상태 포함)과 줄 단위로 대조 · 프로토타입 `Explored` 회귀 테스트 · 포도 회귀.
  - 지금 테스트는 나눠 돈 결과와 끝까지 돈 결과만 비교한다(둘 다 새 코드) → 정답 대조 없이 테스트 통과만으로 "같다"고 하지 않는다.
- **`Brush`가 false인데 배열을 건드리는 경우**: 지금 `Sweep`은 바뀔 때만 쓴다. 나중에 이 성질이 깨지면 1단계가 조용히 틀린다 → `Expand` 주석에 이 전제를 적는다. 붓질 규칙을 바꿀 때는 회귀 테스트가 같이 잡는다.
- **메모리**: 1 · 2단계는 줄기만 한다(받아들인 상태 배열은 지금도 만든다). 3단계는 막힌 키만큼 늘어난다 — 그래서 측정 뒤에 정한다.
- **저장 데이터 호환**: 없음(저장 형식 · 진행 기록 키 · 스테이지 파일을 건드리지 않는다).
- **빌드 용량**: 코드 몇 줄 — 무시할 크기. WebGL 빌드를 하면 `BuildHistory.md`에 적는다.
- **WebGL 제약**: 스레드 · 파일 없음. 탐색을 나눠 도는 방식(`Step(예산)` — 상태 하나의 모든 획을 본 뒤에만 멈춤)은 그대로라, 작업 배열이 `Step` 호출 사이에 걸쳐 남을 일이 없다.
- **측정 잡음**: 에디터 시간은 흔들린다 → 3회씩 · 같은 에디터 세션에서 앞뒤로 잰다. 할당 바이트가 주된 지표.

## 후보 기획(GDD §7)을 불가능하게 만드는지

- 이동 횟수 제한: 솔버 결과(최소 수)가 그대로라 영향 없음.
- 흰색: 색 비트가 늘면 `StateKey`의 칸당 비트 · `MaxCells`를 바꿔야 하는 것은 지금과 같다. 이 계획은 키 형식을 건드리지 않는다.

## 사용자에게 물은 것 — 답(2026-11-19 "권장대로 넣어둬라", 모두 권장대로)

1. 막힌 상태를 기억할까? → **재 보고 정한다.** 0단계 통계로 다시 판정하는 비율을 보고, 3단계에서 직접 잰다. 호박 막다른 길 힌트 시간(에디터 3회 중앙값)이 2단계보다 10% 이상 줄 때만 남기고, 아니면 되돌린다. 결과는 `DECISIONS.md`에 적는다.
2. 대기열을 배열 대신 상태 키로 들고 다닐까? → **이번에는 하지 않는다.** Task 문구 범위가 아니다. 1 · 2단계 측정에서 받아들인 상태 배열이 크게 남으면 그때 따로 항목을 만든다.
3. WebGL 빌드 · 배포와 PC Chrome 힌트 시간 실측까지 할까? → **한다(4단계).** 바꾸는 이유가 런타임 힌트이고, 에디터 Mono와 WebGL GC는 다르게 움직인다(`CLAUDE.md` §6 "빌드로 확인").
